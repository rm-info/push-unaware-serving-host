# PUSH — Push Unaware Serving Host: original design brief

> Historical document: the brief the project started from. The open questions it lists (§13) have since been settled; see [`CLAUDE.md`](../CLAUDE.md) for the decisions and [`operations.md`](operations.md) / [`api.md`](api.md) for what was actually built.

## 1. In one sentence

A small **generic, self-hosted server that knows nothing**: any PWA tells it "send a Web Push to this device at this time, with this opaque ID", and it does so at the right moment without knowing the content, the purpose or the user.

Name: **PUSH** = *Push Unaware Serving Host* (a recursive acronym, PHP-style): a host that serves things it knows nothing about. The last word ("Host") refers to the server itself; the main targets are still phones and tablets. (An earlier name, "Push Unaware Serving Handsets", was dropped: it read as clueless smartphones doing the serving.)

## 2. Why this project exists

- The project started from a medication-reminder app (medicine cabinet stock, intake reminders) whose core relies on **notifications**, and which had to reach iPhone users **without paying Apple's $99/year** developer fee, by shipping it as a **PWA**.
- Established iOS constraints:
  - Native app signed with a free Apple ID: local notifications work, but **remote push (APNs) is impossible**, and the app must be re-signed every 7 days.
  - **PWA: Web Push works for free** (iOS 16.4+, the PWA must be added to the Home Screen, permission must be requested after a user gesture).
  - A PWA **cannot schedule reliable local notifications** while closed → a server must trigger the pushes on time.
- Such apps often have a **fully local mode** (data stays on the phone, no server). That mode must not be forced through an account or a sync server → hence a minimal server dedicated to pushes.
- PUSH is **fully independent from any client app** (its own repository and lifecycle) and reusable by any PWA. The original app is just one client among others.

## 3. How it works

1. The PWA subscribes to Web Push (service worker + the server's public VAPID key).
2. For each reminder, the PWA calls the PUSH API with: the **push subscription**, a **schedule** (one-off time or recurring rule), an **opaque ID** (UUID generated by the PWA).
3. At the scheduled time, the server sends a push whose payload contains **only the ID**.
4. The service worker reads the ID, looks up the reminder text **locally** (IndexedDB) and shows the notification.

→ The reminder content **never leaves the phone**. No message encryption to manage, no key to distribute. Zero health data on the server.

## 4. Data stored on the server (and nothing else)

| Data | Detail |
|---|---|
| Application | API key / app identifier (see §6) |
| Push subscription | endpoint + `p256dh` / `auth` keys provided by the browser |
| Opaque ID | The PWA's UUID, sent back as-is in the push |
| Schedule | One-off: UTC date/time. Recurring: a simple rule (e.g. "every day at 8:00") **+ the device's IANA time zone** so that DST changes don't shift anything |
| Management token | Generated at creation, required to modify/delete. No user account |

## 5. API (3 routes minimum)

- **Create a reminder**: subscription + ID + schedule (+ app key) → returns the management token.
- **Delete a reminder**: ID + management token.
- **List a subscription's reminders**: subscription + token, so the PWA can resync.

Also needed: a route exposing the public VAPID key, and a health endpoint.

## 6. Multiple applications

PUSH must serve several PWAs:
- An **application** concept with an **API key**; each app's reminders are isolated from the others.
- Allows limiting abuse **per application** (quotas).
- **A single VAPID key pair for the whole server.** Caution: a push subscription is bound to the public VAPID key it was created with → if it changes, **every subscription dies**. Backing up this key is mandatory.
- No logic or mention of any specific client app in the code or the API: keep the API clean and generic.

## 7. Scheduling / sending

- Runs **every minute**.
- Selects reminders whose time has come and sends the push (standard Web Push protocol, VAPID, payload = ID only).
- One-off reminder: deleted after sending. Recurring: next occurrence computed (time zone aware).
- If the push service says the subscription no longer exists (**404 / 410**): delete every reminder of that subscription.
- Reasonable retries, and a catch-up policy if the server was down (send "missed" reminders anyway, or skip them? to be decided).

## 8. Client PWA side (to document for integrators)

- On each push, the service worker: reads the ID → looks up the text in IndexedDB → shows the notification.
- **Mandatory on iOS: always show a visible notification.** If the ID is not found locally, show a generic message ("Reminder"). Otherwise Safari may **revoke the subscription**.
- Notification permission requested after a user gesture, once installed on the Home Screen.
- Provide a small client example (JS snippet: subscription + API call + service worker).

## 9. Limits to accept and communicate

- Apple **does not guarantee delivery** of pushes. For medication reminders this matters: say so clearly to end users.
- If the PWA is removed from the Home Screen or the permission revoked, the subscription dies: the server can only notice when a send fails.
- In a PWA, there are no scheduled local notifications outside the server: everything goes through PUSH.

## 10. Privacy

- No health data, no medication name, no reminder text on the server.
- A push subscription identifies a device, but carries no personal information.
- The server "doesn't know what it does or why": that is the design principle, to be preserved in every evolution.
- No content logging; minimal, purged logs.

## 11. Deployment

- Self-hosted, as a **separate service** (it may share a machine with other services, but has its own port and scheduler).
- Behind a reverse proxy with a **Let's Encrypt** certificate (HTTPS is mandatory for Web Push).
- Target platforms: **Linux and Windows**. Provide a simple binary and a Docker image.
- Lightweight, without heavy dependencies: ideally a single process, SQLite, no Redis, no message broker.

## 12. Implementation options considered

- **Start from an existing small Go project** (SQLite, VAPID, no vendor lock-in) and add a scheduling table + scheduler. To check: license, and absence of native scheduling.
- Other small existing projects: an HTTP API + CLI notification server on a single Bun process with SQLite and a Docker image; a Web Push service with subscriptions, campaigns, scheduling, retries and an admin dashboard, without Firebase.
- Or **write our own** on top of a `web-push` library (Node, Go…): estimated at one evening for the core.
- These are small repositories: **audit them before trusting them**.
- Technical points: the VAPID subject needs a **real contact address** (`mailto:`), Apple rejects fake values; HTTPS is mandatory.

## 13. Open questions (to settle at the start)

1. Language / stack: Go, Node/Bun, other?
2. Fork an existing project or start from scratch?
3. Exact format of the recurrence rule (simplified cron, weekdays + time, interval?).
4. Quota policy per application and per subscription (anti-abuse).
5. App authentication: simple API key, or request signing?
6. Behaviour after server downtime (catching up on missed reminders).
7. Minimal admin interface to register applications (is a CLI enough?).
8. Repository name: "push" is very generic and hard to search for; consider a more distinctive repository name while keeping PUSH as the everyday name.
9. Project license (PUSH could be open source).

## 14. Suggested first steps

1. Settle the stack and initialize the repository (README, license, `.gitignore`, Dockerfile).
2. SQLite data model: `apps`, `reminders` (subscription, opaque_id, schedule, tz, manage_token_hash, next_run_at).
3. VAPID key generation / loading (persisted, with a backup warning).
4. The 3 routes + public VAPID key + health, authenticated with the app key.
5. Minute scheduler: selection, Web Push sending (payload = ID), recurrence computation, cleanup on 404/410.
6. Tests: time zones and DST, one-off/recurring reminders, dead subscriptions, isolation between apps.
7. Demo client: a mini PWA (service worker + IndexedDB) to test on a real iPhone added to the Home Screen.
8. Integration documentation for third-party PWAs, with the iOS "always show a notification" pitfall.
